Energy-Aware Scheduling for AI Data Centers: Problem Definition, Formulation, and Research Path

This brief summarizes the optimization problem, current MILP baseline, constraints, modeling assumptions, and the intended evolution from a static deterministic scheduler toward a dynamic decision framework.

1. Problem and Goal

We study a deterministic scheduling problem for an AI data center running flexible GPU workloads over a finite time horizon. Jobs must be assigned to a compatible compute partition and a feasible start time while respecting resource, time, and energy constraints.

The business question is: can flexible AI workloads be shifted in time and across heterogeneous GPU pools to reduce energy cost and grid-import peak without violating operational requirements?

Optimization Output

  • Start time for each flexible job.
  • Compute partition assignment for each job.
  • Renewable and grid energy usage by time slot.
  • Battery charge/discharge/SOC when enabled.
  • Grid-import peak and cost components.
Primary objective: minimize the total operating cost from renewable energy, grid energy, grid-import peak charge, and later service-level tardiness penalties.

2. Scope and Core Assumptions

Current Baseline Is

  • A static deterministic MILP over a representative horizon.
  • An aggregate compute-partition scheduler.
  • Resource-aware: GPU type/count, CPU, memory, and IT power.
  • Energy-aware: PUE, renewable availability, grid prices, peak charge.
  • A classical reference for future quantum and hybrid tests.

Current Baseline Is Not

  • Node-level or individual-GPU bin packing.
  • A rolling-horizon controller.
  • A stochastic model of forecast error.
  • A full production battery dispatch optimizer.
  • A full MILP-to-QUBO conversion.

Compute Partition Abstraction

The Alibaba-aligned baseline creates one aggregate partition per GPU type. Each partition has IT power capacity, GPU count, aggregate CPU capacity, and aggregate memory capacity. This is a Layer 0 approximation: it validates the scheduling and energy formulation before attempting node-level placement.

Modeling Element Current Treatment Reason
Workload labels Reporting only Feasibility is based on resources, not invented business categories.
GPU type Compatibility requirement Jobs may be unrestricted or restricted to specific GPU types.
CPU and memory Aggregate partition constraints Improves realism without node-level bin packing.
Inference Fixed baseline load or pre-reserved demand Online inference is treated as non-flexible.

3. Mathematical Formulation

Sets

Symbol Meaning
\(\mathcal{I}\)Flexible jobs.
\(\mathcal{K}\)Compute partitions or GPU-type pools.
\(\mathcal{T}\)Discrete time slots.
\(\mathcal{S}_i\)Feasible start slots for job \(i\).

Key Parameters

Parameter Description
\(d_i\)Duration of job \(i\), in slots.
\(p_i\)IT power demand of job \(i\), in MW.
\(g_i, c_i, m_i\)GPU count, CPU, and memory required by job \(i\).
\(\Gamma_i\)Allowed GPU types for job \(i\). Empty means unrestricted.
\(P_k, G_k, CPU_k, MEM_k\)Power, GPU, CPU, and memory capacities of partition \(k\).
\(B_t\)Fixed IT baseline load at slot \(t\).
\(G^{ren}_t\)Renewable power available at slot \(t\).
\(\pi^{grid}_t, \pi^{ren}, \pi^{peak}\)Grid price, renewable price, and peak charge coefficient.
\(\eta^{pue}_t\)PUE multiplier at slot \(t\).
\(\Delta t\)Slot length in hours.

Decision Variables

Scheduling assignment \[ x_{i,k,s} = \begin{cases} 1, & \text{if job } i \text{ starts on partition } k \text{ at slot } s \\ 0, & \text{otherwise} \end{cases} \]
Energy and peak variables \[ R_t \ge 0,\quad Q_t \ge 0,\quad P^{peak} \ge 0,\quad E^{peak} \ge 0 \] \[ C_t, D_t, SOC_t \ge 0 \quad \text{only when battery is enabled.} \]

Activity and Load

Activity indicator \[ A_{i,s,t} = \begin{cases} 1, & s \le t \le s+d_i-1 \\ 0, & \text{otherwise} \end{cases} \]
Partition and facility load \[ L_{k,t}(x)= \sum_{i \in \mathcal{I}}\sum_{s \in \mathcal{S}_i} p_i A_{i,s,t}x_{i,k,s} \] \[ L^{IT}_t(x)=B_t+\sum_{k \in \mathcal{K}}L_{k,t}(x) \] \[ L^{facility}_t(x)=\eta^{pue}_t L^{IT}_t(x) \]

4. Constraints

Assignment and Domain Reduction

Each job scheduled exactly once \[ \sum_{k \in \mathcal{K}}\sum_{s \in \mathcal{S}_i}x_{i,k,s}=1 \quad \forall i \in \mathcal{I} \]

Variables are created only when the job-partition pair is compatible and the start slot lies inside the job window. This prunes infeasible decisions before Gurobi or any quantum method sees the instance.

Compatibility Rules

Rule Condition
GPU quantity \(g_i \le G_k\)
GPU type \(\Gamma_i = \emptyset\) or \(\gamma_k \in \Gamma_i\)
CPU compatibility \(c_i \le CPU_k\), when CPU constraints are enabled.
Memory compatibility \(m_i \le MEM_k\), when memory constraints are enabled.

Per-Partition Capacity

Power capacity \[ \sum_i\sum_s p_iA_{i,s,t}x_{i,k,s}\le P_k \quad \forall k,t \]
GPU, CPU, and memory capacity \[ \sum_i\sum_s g_iA_{i,s,t}x_{i,k,s}\le G_k \quad \forall k,t \] \[ \sum_i\sum_s c_iA_{i,s,t}x_{i,k,s}\le CPU_k \quad \forall k,t \] \[ \sum_i\sum_s m_iA_{i,s,t}x_{i,k,s}\le MEM_k \quad \forall k,t \]
Important limitation: satisfying aggregate GPU, CPU, memory, and power constraints does not guarantee node-level feasibility. This is an accepted Layer 0 approximation.

5. Energy, PUE, Battery, and Objective

Energy Balance

Without battery \[ R_t + Q_t = L^{facility}_t(x) \quad \forall t \]
With battery \[ R_t + Q_t + D_t = L^{facility}_t(x)+C_t \quad \forall t \] \[ R_t \le G^{ren}_t \quad \forall t \]

Battery State of Charge

Current simplified battery model \[ SOC_t = SOC_{t-1}+\eta^c C_t\Delta t -\frac{D_t\Delta t}{\eta^d} \] \[ 0\le C_t,D_t\le P^{bat},\quad 0\le SOC_t\le E^{bat} \]

Peak Charge

Grid-import peak \[ P^{peak}\ge Q_t \quad \forall t \] \[ E^{peak}\ge P^{peak}-P^{contracted} \]

Objective Function

Current objective \[ \min \left[ \sum_{t\in\mathcal{T}} \left( \pi^{ren}R_t+\pi^{grid}_tQ_t \right)\Delta t +\pi^{peak}E^{peak} \right] \]
Near-term extension with soft deadlines \[ \min \left[ \text{energy cost} +\text{peak cost} +\sum_{i,k,s} w_i \tau_{i,s}x_{i,k,s} \right] \] where \(\tau_{i,s}=\max(0,s+d_i-\text{deadline}_i)\) is precomputed.

Current vs Proposed Energy Layers

Layer Current Baseline v0.2 / Research Extension Recommendation
PUE Scalar or exogenous time-varying \(\eta^{pue}_t\). Thermal component times load-utilization component. Adopt thermal first
Load-dependent PUE Not modeled. Utilization tranches with big-M selection. Defer
Battery Continuous charge/discharge/SOC with fixed efficiency. SOC-dependent efficiency and no simultaneous charge/discharge. Add mode binary if needed
Service levels Hard windows only. Soft-deadline weighted tardiness. Adopt next

6. Static Versus Dynamic Approach

Static Optimization

A full representative horizon is optimized at once using known jobs, prices, renewable generation, baseline load, and resource capacities.

  • Best for formulation validation.
  • Best for Gurobi benchmarks and optimality gaps.
  • Best for tiny absurd tests and thesis-ground truth.
  • Assumes deterministic inputs.

Dynamic Framework

Scheduling is repeated over time as new forecasts, arrivals, and cluster states become available.

  • Closer to operational deployment.
  • Can reserve capacity for inflexible inference first.
  • Can use rolling horizon or event-triggered re-optimization.
  • Requires rules for job commitment and rescheduling.

Proposed Dynamic Architecture

1. Forecast Inference demand, renewable generation, grid prices, and ambient conditions.
2. Reserve Fix non-flexible loads and unavailable resources before scheduling flexible jobs.
3. Optimize Solve static MILP or reduced subproblem over a rolling window.
4. Execute Commit near-term decisions, monitor deviations, and repeat.
Dimension Static MILP Dynamic Framework
Goal Validate exact formulation and benchmark optimality. Approximate real operating behavior under forecast updates.
Decision timing All decisions made for the full horizon at once. Decisions made repeatedly as time advances.
Uncertainty Inputs treated as known. Forecast errors and new arrivals can be incorporated.
Quantum role Small subproblem benchmarks against MILP optimum. Potential subroutine for hard local allocation windows.

7. Validation and Experiment Strategy

Why Gurobi First

The MILP is the exact classical reference. Before using genetic algorithms, QUBO, QAOA, PCE, or hybrid approaches, we need a trusted formulation whose constraints and objective behave correctly on hand-checkable cases.

Tiny absurd cases Manually verify every constraint and cost component.
Synthetic stress Test Gurobi scaling and feasible-instance generation.
Alibaba-derived cases Calibrate job duration, GPU demand, and resource distributions.
Quantum-scale cases Small but combinatorially difficult instances for QUBO/PCE.

Key Metrics

Metric Purpose
Objective and cost componentsSeparate energy, peak, and later tardiness effects.
MIP gap and runtimeMeasure classical optimality proof difficulty.
GPU/CPU/memory utilizationAssess resource pressure and bottlenecks.
IT energy vs facility energyVerify PUE is applied once and correctly.
Grid import peakMeasure peak-demand charge exposure.
Renewable consumption and curtailmentMeasure temporal energy alignment.
Battery charge/discharge/SOCVerify storage behavior when enabled.

8. Implementation and Research Roadmap

Phase Content Status
1. Static MILP baseline Assignment, compatibility, GPU/CPU/memory/power, PUE, renewable/grid split, peak charge, optional simple battery. Implemented baseline
2. Validation Tiny absurd instances, resource sanity checks, benchmark instance packs. Active
3. Service differentiation Hard and soft deadlines, weighted tardiness, component reporting. Recommended next
4. Physical realism Thermal PUE from ambient temperature; battery mode constraints if storage is central. Near-term extension
5. Advanced MILP Load-dependent PUE tranches, SOC-dependent battery efficiency, tighter big-M derivations. Defer
6. Quantum and quantum-inspired methods Reduced QUBO first, then QAOA, Pauli Correlation Encoding, quantum-inspired tensor networks, and hybrid decomposition on the same benchmark instances. After baseline validation
Quantum scope caution: the full MILP with continuous battery, energy split, PUE tranches, and peak variables should not be the first quantum target. The first experiments should use a reduced assignment/capacity/energy proxy model and compare decoded schedules against MILP.

Quantum and Quantum-Inspired Evaluation Plan

The quantum track will not be limited to one QUBO implementation. The plan is to use the same small, constrained benchmark instances and compare several alternative encodings or solvers against the MILP reference.

Approach Role in the Thesis First Test Scope Main Risk
QUBO / Ising Baseline quantum-ready formulation. Assignment, compatibility, capacity penalties, and simplified energy/peak proxy. Penalty calibration and variable count.
QAOA Gate-based quantum algorithm applied to the reduced Ising/QUBO model. Tiny instances where exact brute force or MILP optimum is known. Circuit depth, noise, and optimizer instability.
Pauli Correlation Encoding Alternative encoding that may represent many binary variables with fewer qubits. Reduced scheduling QUBO with strict decoded-feasibility checks. Constraint satisfaction after decoding; likely needs iterative-alpha PCE.
Quantum-inspired tensor networks Classical tensor-network method to exploit structure in the QUBO/Ising interaction graph. Small and medium constrained benchmark instances before hardware tests. Performance depends on interaction graph structure and bond dimension.
Hybrid decomposition Use classical optimization for the full problem and quantum/quantum-inspired solvers for hard subproblems. Rolling windows, selected jobs, or overloaded cheap-energy intervals. Choosing subproblems whose solutions improve the global schedule.

9. Open Decisions for Supervisor Discussion

  1. Should battery be allowed to charge from the grid, or only from surplus renewable energy?
  2. Should final battery SOC be a minimum or equality constraint for fair scenario comparisons?
  3. Should PUE be facility-wide, cooling-regime-specific, or partition-specific?
  4. What data source should calibrate thermal PUE and renewable profiles?
  5. Do business requirements include soft-deadline jobs, or are all deadlines hard?
  6. Should load-dependent PUE be part of the thesis core or framed as an advanced extension?
  7. For quantum computing, which benchmark ladder should be shared across QUBO, QAOA, PCE, tensor networks, and hybrid methods?
  8. How should dynamic scheduling be evaluated: rolling horizon, event-triggered re-optimization, or static benchmarks only?
