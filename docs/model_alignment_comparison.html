Key Modeling Differences

1. Contracted Power And Peak Billing

Ciro's model currently uses an excess-only peak expression:

peak_penalty = lambda_peak * max(0, peak_load - P_LIM)

The current repository model uses two separate concepts:

  • peak_over_contract = max(0, max_t(total_load_t) - contracted_power).
  • peak_cost = peak_price * peak_over_contract.

Implication. Both models should now allow schedules above contracted power if the excess peak charge is paid. This is a soft economic condition, not a feasibility condition.

2. Average Power Vs Peak Power

Ciro's job data distinguishes:

  • e_kw_avg: used for energy consumption and energy cost.
  • e_kw_peak: used for capacity and peak-demand calculations.

The current repository model uses one job power value for all purposes. Ciro's distinction is more detailed and may be worth adopting if we trust the generated values.

3. Renewable Dispatch Logic

Ciro's model lets the solver choose renewable or grid supply subject to renewable availability. This is appropriate if renewable energy is a contract/pricing option.

The repository model assumes dedicated solar is physically available behind the data center or contractually taken first. It therefore uses available solar before grid energy.

Decision: Should renewable and grid be economically dispatched hour by hour?

4. Cost Of Unused Renewable Energy

Both models should charge renewable cost on renewable energy consumed. Unused renewable availability is reported as curtailment.

This makes the optimizer sensitive to the relationship between renewable price and grid price in each hour.

5. GPU Capacity

The repository model enforces GPU capacity per cluster and hour. Ciro's classical notebook reads the gpus column but does not appear to include a GPU-capacity constraint.

If GPU availability is real, this should remain a hard constraint in the aligned model.

Recommended Alignment Choices

A. Contracted power: Treat as a soft threshold with excess peak charge.

B. Peak charge: Charge only the maximum load above contracted power: peak_price * max(0, peak_load - contracted_power).

C. Job power: Consider adopting e_kw_avg for energy cost and e_kw_peak for physical capacity/peak constraints.

D. Renewable handling: Decide explicitly between dedicated solar consumed first and economic renewable/grid dispatch.

E. Infeasible cases: Do not compare objective values for infeasible runs. Mark them as infeasible and stop extraction.

Proposed Meeting Questions

  1. What contracted-power value should be used?
  2. What excess peak price should be used?
  3. Should jobs have both average and peak power values?
  4. Should cluster capacity be checked against average power, peak power, or both?
  5. Is solar physically dedicated to the data center or only indirectly sourced through the grid?
  6. Do we pay for all contracted solar availability or only consumed renewable energy?
  7. Should GPU capacity be included in every classical and QUBO formulation?
  8. Which baseline inference load should be used: 7.28 kW, 10 kW, or another value?

Bottom Line

Ciro's notebooks are valuable for exploring the idea, especially the average-vs-peak power split and the initial QUBO variable construction. The main remaining Layer 0 alignment topics are average-vs-peak job power, GPU-capacity consistency, baseline load value, and the exact cost parameters.
