1. What We Are Trying To Do

The notebook builds a QUBO for a reduced data center scheduling problem. A QUBO assigns an energy to every binary schedule:

\[ H(z)=q_0+\sum_i q_i z_i+\sum_{i<j}q_{ij}z_i z_j \]

Each binary variable \(z_i\) is either a job assignment decision \(x_{j,k,s}\) or an auxiliary slack bit \(y_{k,t,b}\). A good schedule is a low-energy binary string. The optimization target is:

\[ z^\star=\arg\min_z H(z) \]
Main idea: a tensor network rewrites the large objective over all binary variables as a product or sum of smaller local tensors. Solving then becomes a structured contraction problem instead of plain brute-force enumeration.

2. Tensor Basics

A tensor is a multidimensional array. The number of indices is called the tensor rank.

Object Notation Rank Example shape
Scalar \(a\) 0 one number
Vector \(v_i\) 1 \(2\)
Matrix \(M_{ij}\) 2 \(2\times2\)
Higher-order tensor \(T_{ijk\ell}\) 4 \(2\times2\times2\times2\)

In our QUBO application, every decision variable is binary. Therefore every tensor index has dimension 2, corresponding to values 0 and 1.

Contraction

Tensor contraction means summing over a shared index. Matrix multiplication is the simplest familiar example:

\[ C_{ik}=\sum_j A_{ij}B_{jk} \]

The index \(j\) appears in both tensors and is summed out. Tensor networks generalize this idea to many tensors and many shared indices.

3. What A Tensor Network Represents

A tensor network is a graph. Nodes are tensors. Edges are tensor indices. If an edge connects two tensors, those tensors share an index. Contracting the network eliminates internal indices and produces a scalar, vector, matrix, or another tensor.

For optimization, we can view a tensor network as a compressed representation of a huge table. A brute-force table over \(n\) binary variables has \(2^n\) entries. A tensor network stores local pieces of that table and combines them only as needed.

4. Deriving A Tensor Network From A QUBO

Start from the QUBO:

\[ H(z)=q_0+\sum_i q_i z_i+\sum_{i<j}q_{ij}z_i z_j \]

A standard statistical-mechanics transformation defines the Boltzmann weight:

\[ W(z)=\exp[-\beta H(z)] \]

where \(\beta\) is inverse temperature. Large \(\beta\) concentrates weight on low-energy configurations. The partition function is:

\[ Z(\beta)=\sum_z \exp[-\beta H(z)] \]

Since the QUBO is a sum of local terms, the exponential factorizes:

\[ Z(\beta) = e^{-\beta q_0} \sum_z \prod_i \exp(-\beta q_i z_i) \prod_{i<j}\exp(-\beta q_{ij}z_i z_j) \]

Unary tensors

For each linear term \(q_i z_i\), create a rank-1 tensor:

\[ U_i(z_i)=\exp(-\beta q_i z_i) \]

Since \(z_i\in\{0,1\}\):

\[ U_i= \begin{bmatrix} 1 \\ e^{-\beta q_i} \end{bmatrix} \]

Pair tensors

For each quadratic term \(q_{ij}z_i z_j\), create a rank-2 tensor:

\[ V_{ij}(z_i,z_j)=\exp(-\beta q_{ij}z_i z_j) \]

Its table is:

\[ V_{ij}= \begin{bmatrix} 1 & 1 \\ 1 & e^{-\beta q_{ij}} \end{bmatrix} \]
Optimization version: instead of summing products of exponentials, we can work directly in the energy domain and replace ordinary summation with minimization. This is called min-sum contraction or zero-temperature contraction.

5. Applying This To The Scheduling QUBO

The notebook builds the total Hamiltonian:

\[ H_{\text{total}} = H_{\text{energy}} + H_{\text{assign}} + H_{\text{GPU}} + H_{\text{peak}} \]

Decision indices

The main scheduling decision is:

\[ x_{i,k,s}=1 \]

if job \(i\) starts on cluster \(k\) at start slot \(s\). Incompatible job-cluster combinations are omitted before the QUBO is built. GPU capacity uses slack bits:

\[ y_{k,t,b}\in\{0,1\} \]

Energy cost factors

In fixed-PUE mode, energy cost is linear:

\[ H_{\text{energy}} = \sum_{i,k,s} \left( \sum_t c_t \Delta t\, PUE_t\,p_i\,a_{i,s,t} \right) x_{i,k,s} \]

Tensor-network meaning: each assignment variable gets a unary factor. Expensive hours raise the unary cost of starts that make a job active in those hours.

Assignment factors

Each job must be assigned exactly once:

\[ \sum_{(k,s)\in\mathcal A_i} x_{i,k,s}=1 \]

The penalty is:

\[ H_{\text{assign}} = \lambda_A \sum_i \left( \sum_{(k,s)\in\mathcal A_i}x_{i,k,s}-1 \right)^2 \]

Tensor-network meaning: for each job \(i\), create one local factor connected to all assignment variables belonging to that job. The factor has zero or low energy when exactly one option is selected, and high energy otherwise.

GPU capacity factors

GPU usage for cluster \(k\) at time \(t\) is:

\[ D^G_{k,t}(x)=\sum_i\sum_s g_i a_{i,s,t}x_{i,k,s} \]

The notebook converts the inequality \(D^G_{k,t}(x)\leq G_k\) into an equality using binary unused-capacity slack:

\[ D^G_{k,t}(x)+\sum_b2^b y_{k,t,b}=G_k \]

The penalty is:

\[ H_{\text{GPU}} = \lambda_G \sum_{k,t} \left( D^G_{k,t}(x)+\sum_b2^b y_{k,t,b}-G_k \right)^2 \]

Tensor-network meaning: for every cluster-hour pair, create a local tensor connected only to the assignment variables active on that cluster-hour plus the slack bits for that cluster-hour.

Peak smoothing factors

For fixed PUE, the peak proxy is:

\[ H_{\text{peak}} = \lambda_P \sum_t \left( PUE_t L^{IT}_t(x) \right)^2 \]

where:

\[ L^{IT}_t(x)=\sum_{i,k,s}p_i a_{i,s,t}x_{i,k,s} \]

Tensor-network meaning: for each hour \(t\), create one factor connected to all assignment variables active during that hour. This factor discourages concentrated load.

6. How The Solver Contracts The Network

The exact solver added in src/quantum/tensor_network.py uses min-sum variable elimination. It works in the energy domain, so local tensors store energy contributions rather than Boltzmann probabilities.

  1. Create one unary energy tensor for every QUBO linear term.
  2. Create one pair energy tensor for every QUBO quadratic term.
  3. Choose a contraction order over binary variables.
  4. For the next variable, collect every factor that touches it.
  5. Add those factors into one combined tensor.
  6. Minimize over the selected variable and keep the remaining tensor.
  7. Store the local argmin choice so the best binary sample can be reconstructed.

Mathematically, if a bucket contains factors depending on \(z_i\) and neighboring variables \(z_{\partial i}\), the solver computes:

\[ F_{\text{new}}(z_{\partial i}) = \min_{z_i\in\{0,1\}} \sum_{F\in\text{bucket}(i)} F(z_i,z_{\partial i}) \]
Important scaling point: exact tensor contraction can still be exponential. The cost is controlled less by the total number of variables and more by the largest intermediate tensor produced during contraction.

The implementation reports:

  • energy
  • sample
  • elapsed_seconds
  • contraction_order
  • max_factor_rank
  • max_factor_size

7. Why Tensor Networks Are Valuable Here

Brute force enumerates every binary string:

\[ \text{cost}_{\text{brute force}}\sim 2^n \]

Tensor contraction exploits the interaction graph. If the graph has low effective width, the cost behaves more like:

\[ \text{cost}_{\text{tensor}}\sim n\,2^w \]

where \(w\) is related to the largest number of mutually coupled variables encountered during contraction. This is why a sparse or structured 80-variable QUBO can be easier than a dense 35-variable QUBO.

Why our scheduling model has exploitable structure

  • Compatibility filtering removes invalid job-cluster variables before optimization.
  • Assignment constraints connect variables for the same job, not all jobs globally.
  • GPU capacity factors are local to a cluster and hour.
  • Activity coefficients \(a_{i,s,t}\) create time-local interactions.
  • Narrow start windows reduce the number of variables connected to each factor.

The open question is therefore not only how many QUBO variables we have. The better question is:

Can compatibility filtering, time-window narrowing, and cluster-hour locality keep the tensor network's effective width small enough for contraction to beat brute force and compete with heuristic solvers?

8. Practical Evaluation Plan

Use exact tensor contraction first on tiny and small slices. That gives a correctness reference before introducing approximate tensor methods.

Recommended experiment ladder

  1. Start with the toy QUBO from the notebook and verify exact agreement with brute force.
  2. Increase the number of jobs while keeping start windows narrow.
  3. Measure how max_factor_rank and max_factor_size grow.
  4. Compare tensor contraction runtime against brute force until brute force becomes infeasible.
  5. Compare energy and feasibility against simulated annealing or D-Wave Ocean samples.
  6. When exact contraction becomes too expensive, move to approximate tensor-network methods.
Study takeaway: tensor networks are valuable here because they expose the structure hidden inside the QUBO. The scheduling problem is not just a flat binary string. It is a graph of assignment, time, cluster, capacity, and peak-load relationships. Tensor methods let us measure and exploit that graph structure directly.
