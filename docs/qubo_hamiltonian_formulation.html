1. QUBO Scope and Modeling Boundary

This document focuses only on the reduced QUBO formulation. The goal is not to reproduce the full operational optimization model. Instead, the QUBO isolates the binary scheduling core that can be sent to D-Wave, QAOA, Pauli Correlation Encoding, tensor-network methods, or other QUBO/Ising-compatible solvers.

Core idea. The QUBO chooses whether each job runs on a compatible cluster at a feasible start time. Feasibility constraints are converted into Hamiltonian penalties, and costs are encoded as linear or quadratic coefficients.

The current reduced QUBO includes assignment, GPU capacity, energy cost, fixed/exogenous PUE, an optional load-dependent PUE energy term, and a peak/load-smoothing proxy. It intentionally does not include battery state of charge, explicit renewable/grid dispatch variables, exact contracted peak billing, or continuous energy-balance variables.

2. QUBO Variables, Compatibility, and Activity

2.1 Assignment Variables

The fundamental binary variable is one complete scheduling option:

Assignment decision \[ x_{i,k,s}=\begin{cases} 1, & \text{job }i\text{ starts on cluster }k\text{ at slot }s,\\ 0, & \text{otherwise.} \end{cases} \]

The QUBO does not create variables for impossible combinations. If a job is not compatible with a cluster, all corresponding \(x_{i,k,s}\) variables are omitted before the Hamiltonian is built.

Feasible option set \[ \mathcal{A}_i=\{(k,s): C_{i,k}=1,\ s\in\mathcal{S}_i\} \]
SymbolMeaning
\(\mathcal{I}\)Set of jobs.
\(\mathcal{K}\)Set of clusters or aggregate GPU partitions.
\(\mathcal{S}_i\)Feasible start slots for job \(i\).
\(C_{i,k}\)Compatibility relation. It is 1 if job \(i\) can run on cluster \(k\).
\(\mathcal{A}_i\)Set of feasible cluster-start options for job \(i\).

2.2 Activity Coefficient

Activity is precomputed data, not a decision variable. It tells us which time slots are occupied if a job starts at a given slot.

Precomputed activity \[ a_{i,s,t}=\begin{cases} 1, & s\le t

Once the solver selects \(x_{i,k,s}=1\), the coefficient \(a_{i,s,t}\) determines where the job contributes power and GPU load. This is why the QUBO does not need extra variables for “job is active”.

2.3 Load Expressions

These expressions are used later to build energy, GPU, and peak terms.

IT power load \[ L_t^{IT}(x)=\sum_{i\in\mathcal{I}}\sum_{k\in\mathcal{K}}\sum_{s\in\mathcal{S}_i} p_i a_{i,s,t}x_{i,k,s} \]
GPU demand by cluster and time \[ D^G_{k,t}(x)=\sum_{i\in\mathcal{I}}\sum_{s\in\mathcal{S}_i} g_i a_{i,s,t}x_{i,k,s} \]

3. Generic Squared-Penalty Expansion

The notebook implements constraints using a generic helper that expands squared equalities into QUBO coefficients. For binary variables \(z_r\in\{0,1\}\), consider:

Generic squared equality \[ H_{penalty}=\lambda\left(\sum_{r\in R}a_rz_r-b\right)^2 \]

Expanding the square gives:

Expansion \[ \begin{aligned} H_{penalty} &=\lambda\left[ \left(\sum_{r\in R}a_rz_r\right)^2 -2b\sum_{r\in R}a_rz_r+b^2 \right]\\ &=\lambda\left[ \sum_{r\in R}a_r^2z_r^2 +\sum_{r\in R}\sum_{\substack{q\in R\\q\ne r}}a_ra_qz_rz_q -2b\sum_{r\in R}a_rz_r+b^2 \right]. \end{aligned} \]

Because variables are binary, \(z_r^2=z_r\). Therefore:

\[ H_{penalty}=\lambda b^2 +\sum_{r\in R}\lambda(a_r^2-2ba_r)z_r +\sum_{r\in R}\sum_{\substack{q\in R\\q\ne r}}\lambda a_ra_qz_rz_q \]

The formula above writes ordered pairs \(q\ne r\). The implementation stores each unordered QUBO interaction once, so it adds \(2\lambda a_ra_q\) for the stored pair \((r,q)\). This is the same mathematics with a more efficient coefficient representation.

QUBO componentCoefficient added by the helper
Offset\(+\lambda b^2\)
Linear term for \(z_r\)\(+\lambda(a_r^2-2ba_r)\)
Quadratic term for stored pair \(z_rz_q\), \(r<q\)\(+2\lambda a_ra_q\)

4. Hamiltonian Terms in Notebook Order

4.1 Energy Cost Term

The notebook starts with the energy cost term. Under fixed or exogenous PUE, each assignment variable receives a linear cost equal to the price of the time slots in which the job would be active.

Per-option energy coefficient \[ E_{i,k,s}=\sum_{t\in\mathcal{T}}c_t\Delta t\,PUE_t\,p_i\,a_{i,s,t} \]
Energy Hamiltonian \[ H_{energy}^{fixed}=\sum_{i,k,s}E_{i,k,s}x_{i,k,s} \]
Validation meaning. With only this term, the optimal solution schedules no jobs because all scheduled work has positive cost. This is correct: the cost term prices work, but does not force work to happen.

4.2 Assignment Constraint Penalty

Next, every job must be selected exactly once from its feasible options:

\[ \sum_{(k,s)\in\mathcal{A}_i}x_{i,k,s}=1 \]

The QUBO penalty is:

\[ H_{assign}=\lambda_A\sum_{i\in\mathcal{I}} \left(\sum_{(k,s)\in\mathcal{A}_i}x_{i,k,s}-1\right)^2 \]

For one job, define \(z_r\) as each feasible option in \(\mathcal{A}_i\). This is the generic squared penalty with \(a_r=1\) and \(b=1\):

Expanded assignment penalty for one job \[ \lambda_A\left[ 1- \sum_{r\in\mathcal{A}_i}z_r + \sum_{r\in\mathcal{A}_i}\sum_{\substack{q\in\mathcal{A}_i\\q\ne r}}z_rz_q \right] \]

The negative linear part rewards selecting an option. The positive quadratic part penalizes selecting two different options for the same job. The minimum penalty is reached when exactly one option is selected.

4.3 GPU Capacity Constraint With Binary Slack

GPU capacity is an inequality per cluster and time slot:

\[ D^G_{k,t}(x)\le G_k \]

QUBO handles equalities naturally, so the inequality is rewritten using unused-GPU slack \(Y_{k,t}\):

\[ D^G_{k,t}(x)+Y_{k,t}=G_k \]

The slack is encoded in binary:

\[ Y_{k,t}=\sum_{b=0}^{B_k-1}2^b y_{k,t,b}, \qquad B_k=\left\lceil\log_2(G_k+1)\right\rceil \]

The GPU Hamiltonian becomes:

\[ H_{GPU}=\lambda_G\sum_{k,t} \left( \sum_i\sum_s g_i a_{i,s,t}x_{i,k,s} +\sum_{b=0}^{B_k-1}2^b y_{k,t,b} -G_k \right)^2 \]

For one cluster-time pair, the expansion contains assignment-assignment interactions, assignment-slack interactions, slack-slack interactions, linear terms, and the constant \(\lambda_GG_k^2\). If usage is below capacity, slack can represent the unused GPUs and the penalty can be zero. If usage exceeds capacity, no non-negative slack can repair the equality, so the penalty is positive.

4.4 Peak Penalty

After assignment and GPU capacity, the notebook adds a peak or load-smoothing proxy. With fixed PUE, the proxy uses squared facility load:

\[ H_{peak}^{fixed}=\lambda_P\sum_t\left(PUE_tL_t^{IT}(x)\right)^2 \]

This is still a QUBO because \(PUE_t\) is constant and \(L_t^{IT}(x)\) is linear in the binary assignment variables.

Expanded peak term for one time slot \[ \lambda_P\left(\sum_r \ell_{r,t}x_r\right)^2 =\lambda_P\left[ \sum_r\ell_{r,t}^2x_r +\sum_r\sum_{q\ne r}\ell_{r,t}\ell_{q,t}x_rx_q \right] \]

where \(\ell_{r,t}=PUE_t p_i a_{i,s,t}\) for assignment option \(r=(i,k,s)\). The positive interactions make simultaneous load more expensive than spread load.

5. PUE Integration

PUE converts IT load into facility load. It is not modeled as a separate feasibility constraint in the QUBO; it modifies the cost terms.

5.1 Fixed or Exogenous PUE

With fixed or hourly exogenous PUE, PUE is just a known multiplier:

\[ P_t^{fac}(x)=PUE_tL_t^{IT}(x) \]

Therefore both energy and peak remain QUBO-compatible:

\[ H_{energy}^{fixed}=\sum_t c_t\Delta t\,PUE_tL_t^{IT}(x) \] \[ H_{peak}^{fixed}=\lambda_P\sum_t\left(PUE_tL_t^{IT}(x)\right)^2 \]

5.2 Load-Dependent PUE Energy

The notebook also includes an optional affine utilization-dependent PUE energy model:

\[ PUE_t(x)=PUE_{high}-(PUE_{high}-PUE_{low}) \frac{L_t^{IT}(x)}{L_{max}^{IT}} \]

Substituting into facility energy gives:

\[ H_{facility}=\sum_t c_t\Delta t\left[ PUE_{high}L_t^{IT}(x) - \frac{PUE_{high}-PUE_{low}}{L_{max}^{IT}} \left(L_t^{IT}(x)\right)^2 \right] \]

This remains a QUBO because the first part is linear and the second part is quadratic. However, if we also squared load-dependent facility power in the peak term, the result would become cubic and quartic.

QUBO boundary. Under load-dependent PUE, the peak proxy is kept on IT load: \[ H_{peak}^{IT}=\lambda_P\sum_t\left(L_t^{IT}(x)\right)^2. \] This avoids quartic terms and keeps the model as a true QUBO.

6. Final Hamiltonian

The default fixed-PUE notebook Hamiltonian is:

Fixed-PUE QUBO \[ H_{total}^{fixed} =H_{energy}^{fixed}+H_{assign}+H_{GPU}+H_{peak}^{fixed} \]

The optional load-dependent PUE variant is:

Load-dependent PUE QUBO \[ H_{total}^{load} =H_{facility}+H_{assign}+H_{GPU}+H_{peak}^{IT} \]

7. Progressive Validation Flow

The notebook validates the Hamiltonian one term at a time. This is important because a QUBO can be syntactically valid but conceptually wrong if one penalty is expanded incorrectly.

StepHamiltonian includedExpected behavior
1\(H_{energy}\)No jobs are scheduled because energy cost is positive.
2\(H_{energy}+H_{assign}\)Every job is scheduled exactly once, but GPU overloads may occur.
3\(+H_{GPU}\)Schedules respect GPU capacity using slack variables.
4\(+H_{peak}\)Simultaneous load becomes less attractive when the peak weight is strong enough.

Decoded samples must always be checked for assignment feasibility and resource feasibility. Low QUBO energy is not enough if penalty weights are too weak or if the decoded schedule violates constraints.
